# "Add agent to profile" (talents-ai-score Phase 2) — CLI + certs

Owner's decision: SAME model as the portfolio (ADR-059) — the IA PRE-DRAFTS, the talent EDITS. Two repos, both on `feat/talents-ai-score`.

## certs (shakers-certifications-service) — the AI draft endpoint
`POST /api/v1/works/talents/me/agents/draft-fields` — Bearer certs session only (NO X-Hub-Token; never calls Hub). Body `{ consent, name, tools?, model?, parent?, definition? }` -> `{ status:'OK', data:{ whatItDoes, humanDecides } }`.
Built as a near-verbatim mirror of `DraftPortfolioDescriptionService` (ADR-059 §2, commit ee0a31e): CHEAP pinned chain `gemini-2.5-flash -> gpt-4o-mini -> claude-haiku-4-5-20251001`, consent gate FIRST (`input.consent !== true` -> `AiConsentRequiredException` 403), `captureBodyInTrace:false` (the agent `definition` is NDA-adjacent + a prompt-injection vector, never traced), fail-closed (`AgentFieldsUnavailableException` 502 -> CLI free-text fallback). The `@Inject(AnthropicProvider)` at ctor index 2 is MANDATORY (BaseAIService's inherited `@Optional() @Inject` makes the 3rd provider silently undefined otherwise — the repeating DI trap).
Prompt (`agent-fields.prompt.ts`): grounding-only, `definition` fenced as untrusted payload and SUMMARISED (never echoed verbatim), output `{"whatItDoes":"...","humanDecides":"..."}`, both fields required or fail-closed.
KEY STRUCTURAL trick: the declare/list RELAY controller (`WorksTalentAgentsController`, another agent's uncommitted work) and the AI draft controller (`WorksTalentAgentsAiController`, new) share the SAME base route `works/talents/me/agents` with DISJOINT sub-routes (`draft-fields` vs `declare`/``) — Nest allows two controllers on one base path, exactly how portfolio splits AI (`WorksTalentPortfoliosController`) from relay. Register BOTH in `works.module.ts`, and add the new exception CODE to `WorksExceptionFilter.codeMap`.
Verify: `./node_modules/.bin/jest <path>`, `./node_modules/.bin/ts-node scripts/typecheck-gate.ts` (baseline 378 errors — must stay 378), `./node_modules/.bin/nest build` (0 issues). NEVER `biome check --write .` (reformats the whole repo).

## CLI (ai-usage-evaluator) — the `start` route
`src/start-add-agents.js#runAddAgents` replaces the old `addAgents` "coming soon" no-op in `bin/start.js`. Mirror of `start-add-portfolio.js`. Steps: pick detected agent (`collectAgents`), DEDUP by name (`GET .../agents`), name editable, consent -> AI draft `whatItDoes`+`humanDecides` (editable via `askWithDefault`, free-text on decline/no-endpoint/fail), `timeSavedHoursWeek` optional `>=0` (0 is legal — send it), `catalogId` from a prior `usage` classification (`loadAgentClassifications` -> `classification.catalogId`/`.role`, skip floor/unclassified), `isVisible` default true, declare.
`src/agents-client.js` mirrors `portfolio-client.js`: `requestListAgents`/`requestDeclareAgent` carry Bearer + `X-Hub-Token`; `requestDraftAgentFields` carries Bearer ONLY and always sends `consent:true` (caller gates). Optional fields OMITTED not null; `timeSavedHoursWeek:0` sent (finite-number check, not truthiness).
FIELD MAPPING to Hub: send `name, catalogId?, whatItDoes?, humanDecides?, timeSavedHoursWeek?, isVisible?`. The CLI-detected `tools/model/parent` have NO Hub destination — they ONLY feed the AI draft, NEVER sent to declare.
Endpoints in `config.js` (climb-one-segment like skills/portfolio): `getAgentsDeclareEndpoint` (`../works/talents/me/agents/declare`), `getAgentsListEndpoint` (`../works/talents/me/agents`), `getAgentsDraftFieldsEndpoint` (`../works/talents/me/agents/draft-fields`). Overrides `SHAKERS_CLI_AGENTS_{DECLARE,LIST,DRAFT_FIELDS}_ENDPOINT`.
Drain note: `chooseAgent` calls `ask.drain()` after the raw picker resumes (the picker-residual-Enter discipline) — before the name-edit/consent prompt.
REGRESSION: two `test/bin-start-cli.test.js` cases used the old "próximamente" text as the benign loop branch; with no ingest endpoint configured the real route now hits its no-endpoint stderr branch and returns to the loop — assert `stderr /No hay endpoint configurado/` instead. Updated the i18n `menuAddAgentsDesc` (removed "coming soon") in both langs.

## certs BOOT gotcha (found validating add-agent — LESSON: smoke-run a real boot, not just tsc/tests)
tsc-gate + jest all green but the certs container never booted (not listening on :3000). Cause chain was config-namespace DI, unrelated to our add-agent commit b6a0999 (which touches none of langfuse/app.module/config): a `registerAs('ns')` config is only injectable if registered via the root `ConfigModule.forRoot({ load: [...] })` array OR a module's `ConfigModule.forFeature(cfg)`. Post-develop-merge, TWO of 14 namespaces were unregistered — `livekit` (user fixed via env; its module DID `forFeature` so it was a runtime `startsWith` on undefined VALUES, not a DI error) and `langfuse` (LangfuseModule had NO forFeature and langfuse wasn't in the load array → `UnknownDependenciesException: CONFIGURATION(langfuse)` at boot). Fix: add `imports: [ConfigModule.forFeature(langfuseConfig)]` to `LangfuseModule` (mirror LivekitModule — the consuming module owns registering its config). `LangfuseProvider` already tolerates ABSENT keys (warns, disables tracing), so no secret is needed for boot. Verify by BOOT: the `-b swc -w` watch recompiles+restarts on save; confirm via `docker logs` "Nest application successfully started" (timestamp AFTER your edit) + a mounted route returning 401 (not 404). Aside: certs local `dd.service` logs as `shakers-ai-interviewer-back-local` (cosmetic DD_SERVICE misconfig, not a boot issue).
